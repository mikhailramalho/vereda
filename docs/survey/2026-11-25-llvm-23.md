# LLVM 23

Recorded 2026-11-25.

Vereda moved from LLVM 21 to LLVM 23, and builds with 23 only: one version
to build and test. `DOWNLOAD_DEPENDENCIES` looks for `/usr/lib/llvm-23` and
otherwise downloads the official 23.1.6 release; CI installs apt.llvm.org's
LLVM 23 (23.1.6 too). Issue #213 asked for it: rustc 1.100 (LLVM 23.1.5)
writes bitcode that LLVM 21 rejects with "Invalid record". LLVM 23 reads it,
and `tests/vereda/rust_largest` links such bitcode in.

## What changed

LLVM 23's API: `BranchInst` is deprecated, split into `CondBrInst` and
`UncondBrInst`, with opcodes of their own; `PointerMayBeCaptured` with a
mask returns the captures with and without returns, instead of taking
`ReturnCaptures`; `make_absolute` with a directory moved from `sys::fs` to
`sys::path`.

clang 23 and LLVM 23's passes make IR the walker did not take:

- `ptrtoaddr`, new in LLVM 22: InstCombine turns `sprintf(b, "%s", p)` into
  `stpcpy(b, p) - b` and takes that difference through it (esbmc/github_8524_*
  and sprintf_objsize_s_overflow_fail went UNKNOWN). It is a `ptrtoint` that does
  not capture the provenance; Vereda encodes both as the address, and SCEV's
  `scPtrToAddr` as its `scPtrToInt`.
- `cmpxchg` on `ptr` operands, where clang 21 loaded and compared `i64`s
  (esbmc-unix/github_4436 went UNKNOWN). The pointers compare as `icmp eq`
  compares them.
- A sanitizer trap's location: since clang 22, with
  `-fsanitize-debug-trap-reasons` on by default, the trap sits at line 0 of an
  artificial function `__clang_trap_msg$<reason>` inlined at the check, so a
  failed overflow check was reported at line 0 (vereda/sanitize_unsigned and
  two others). `vereda.py` turns the reasons off, which puts the trap back at
  the check.

clang's sanitizer handler list (`SanitizerHandler.h`), which
`ir/sanitizer.h` maps, is the same in 21 and 23.

## Verdicts

The whole suite against main's with LLVM 21 (4f2c0972, with #209; 6881 tests
counting the new Rust one), verdicts from `REGRESS_STATS`: no CORE test
changed. Six FUTURE tests gave another verdict.

Four now give the expected one, and are CORE again. nextafter_from_infinity:
LLVM 23 knows `nextafter` and `nextafterf` of constants and folds the
comparisons of their results; Vereda has no body for them, so on main the
results were nondet. github_7897 (vector comparisons): main stopped at an unsupported
`<8 x i1>` constant with undef lanes, which LLVM 23's passes fold away.
alloca_ptrdiff_max and vla_ptrdiff_max (a stack object of exactly
PTRDIFF_MAX bytes): LLVM 21's `DataLayout` computed an array's size in bits,
so `[N x i8]` with N near 2^63 or 2^64 wrapped (2^63 - 1 bytes came out as
2^61 - 1), and the pointer one past the end fell outside the object. LLVM 23
gives the true size.

Two now say SUCCESSFUL where ESBMC expects FAILED with "alloca: size exceeds
PTRDIFF_MAX", a check Vereda lacks (why they are FUTURE):
alloca_const_above_layable (`__builtin_alloca(-1)`, then `assert(0)`) and
ptr_rel_huge_object_alloca_const (2^63 bytes). With the true size the request
does not fit, and Vereda ends the path there, as it does for any stack object
that does not fit; with LLVM 21's wrapped size (2^61 - 1 bytes, and 0) the
path went on and failed by accident. They are re-marked. ESBMC reports such
a constant request since its R39 change instead of assuming it away; doing
the same would make both FAILED again.

it; `--base-clang` gives each binary its own clang), camada 0.24 in both,

The walk without summaries gets 3 to 9% faster and the solves stay within
2%; github_302's walk is 2 to 3% slower in each of the three runs. The
smaller start (0.03 s and 5 MB less on every test) may come from the build
rather than the version: the branch's LLVM is the release, a ThinLTO build,
main's Ubuntu's plain objects. CI builds both from apt.llvm.org's packages.

For this one pull request, perf.yml cannot build its base: it builds main's
sources against the head's LLVM, and they do not compile against LLVM 23's
API. The numbers above stand in for it.
